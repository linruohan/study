## 一、项目定位与当前架构

「文明重启(Lumen)」:按年龄档规划学习的应用。三部分:

- `app/` — Flutter 客户端(study_app),纸本风格界面,无第三方状态管理/DB 库,HTTP 用 dart:io 手写。
- `server/` — Fastify 5 + zod + pg + S3 兼容对象存储。**依赖服务统一用 Docker 部署**:`server/docker-compose.yml` 已备好 PostgreSQL 16 + MinIO(含数据卷与健康检查),`docker compose up -d` 即可启动,不再依赖 WSL。
- `doc/` — 分龄学习资料与设计文档。

### 数据链路(当前真实形态)

```
设备 UUID(device_id.txt)
   │
   ├─ 启动:先推送 pending 缓存(app/lib/data/study_repository.dart)
   ├─ 并行拉取 GET /api/knowledge(整份知识目录)与 GET /api/devices/:id/data
   ├─ 失败但有缓存 → 离线启动(fromCache 标记)
   └─ 离线修改 → study_cache.json(pending=true),下次联网自动推回
```

- 服务地址由 `--dart-define=API_BASE_URL` 覆盖,默认 `http://127.0.0.1:3000`。
- 知识内容全部在 PostgreSQL,客户端不保留知识副本(`app/lib/knowledge/taxonomy.dart` 只留数据形态)。
- 身份现状仍是设备 UUID、无登录。目标形态:增加**用户登录与管理模块**——普通用户登录后只读,管理员(admin)可编辑一切,见"管理体系"与 P1-3。

### 知识模型(016 迁移后)

```
knowledge_categories(parent_id 嵌套:九类为顶层,原"领域"降为子类)
  → knowledge_concepts(depth / sort_order)
    → 分龄呈现(7 档 age_band)
      → 三档知识点(3 档 degree)
        → 章节 / 评论 / 纠错 / 积分
```

九类分类法见 `doc/九类分类法.md`。年龄目录(doc/readme.md 的蒙学→硕士)与九类是正交的两个维度。

### 三大体系(目标设计,指导后续开发)

#### 1. 知识体系

- 九大类可嵌套:每个类可以有子类(与 012/016 的 `parent_id` 模型一致),类下挂知识(概念)。
- 每一个知识包含**四种认知程度:入门、熟练、精通、创造**。
- 每个认知程度下有多个知识点。
- 与旧"技能四档"的关系:`doc/design.md` 既有技能四档(尝试→熟悉→熟练→掌握)**被本四档取代**,映射为 尝试→入门、熟悉→熟练、熟练→精通、掌握→创造;历史数据与 seed 按此映射归档,文档同步时旧表述只保留在映射说明里。
- ⚠️ 现状差异:数据库当前是 3 档 degree(`knowledge_degrees`),要扩为 4 档,属 schema 变更,走 017+ 迁移;客户端三档 Tab(`knowledge_detail_page.dart`)、智者追加知识点的"本档呈现"逻辑、相关 seed 数据都要同步。

#### 2. 认知体系

认知思维目标层次由低到高、由简到繁分六个层级,层层递进:

**记忆 → 理解 → 应用 → 分析 → 评价 → 创新**

定位:这是"知识点"的属性维度——每个知识点在编写时应标注它训练的是哪个认知层级;学习路径按"低层未过不推高层"组织(与技能四档、分龄呈现正交)。当前数据模型没有认知层级字段,需要新增(如 `knowledge_point_cognitive_level`),知识点 CRUD 接口与详情页筛选随之调整。

#### 3. 知识学位等级体系:九境三阶 · 简化版

学位从"授予的称号"变为"达成的境界"。以能力证据链为验证内核,以「识构通辨创立化宗道」为意象标签。

| 阶 | 境界 | 质变标志 | 对应原学位 |
| --- | --- | --- | --- |
| 初阶 · 入门与结构化 | 识境 | 基础读写算与信息检索,能区分事实与观点 | 高中/预科 |
| 初阶 | 构境 | 独立搭建一个领域的基础知识框架 | 学士 |
| 初阶 | 通境 | 跨子领域整合知识,能迁移到新情境 | 学士后/桥梁 |
| 中阶 · 深化与创造 | 辨境 | 辨识前沿问题与知识缺口,具批判判断力 | 硕士 |
| 中阶 | 创境 | 提出原创性问题或方案,产出知识增量 | 硕士后/博士预备 |
| 中阶 | 立境 | 建立自洽的贡献体系,能独立定义研究议程 | 博士 |
| 高阶 · 引领与范式影响 | 化境 | 知识迁移转化到多领域,产生跨域影响 | 博士后/资深研究者 |
| 高阶 | 宗境 | 形成被同行广泛认可的知识体系或方法论 | 领域领军/资深教授 |
| 高阶 | 道境 | 提出改变多领域基本假设的范式性贡献 | 大师/范式开创者 |

三条运行规则:

1. **达成制**:靠能力证据链达成,不靠年限与单一机构授予。
2. **动态账本**:境界状态持续更新,可升可待更新,授予即定格作废。
3. **可跳跃**:证据链足够即可越境,不强制逐级积累年限。

一句话:九境三阶,以"识构通辨创立化宗道"为意象标签,以能力证据链为验证内核,学位从"授予的称号"变为"达成的境界"。

#### 4. 管理体系

权限模型采用**两级角色**,取代现状"任何设备都能写":

- **普通用户**:登录后只有**查看权限**,无法编辑和修改任何知识内容;可以提交纠错/评论、查看自己的学习数据。
- **管理员**:内置账号 **admin/admin**,可以修改、添加**所有内容**(分类/子类、知识概念、分龄呈现、知识点、章节、审核纠错、授予学位、用户管理)。
- 落地含义:需要新增用户表、登录接口(密码校验 + 会话/token)与管理模块(用户列表、角色管理);所有写接口(categories/concepts/points/chapters/review/sage 审核)加管理员校验,未登录或普通用户调用一律 403。admin 首次登录应强制修改默认密码。
- 境界数据模型:新增**学位表**(如 `user_degrees`:用户、当前境界、阶位、更新时间)与**学位申请表**(如 `degree_applications`:用户、目标境界、证据链内容、状态 pending/approved/rejected、审核人)。证据链按学习知识的**广度**(覆盖的分类/概念数量)与**深度**(各程度档位分布、章节完成情况、纠错/贡献记录)构成,积分与智者贡献可折算为证据项;用户**自行提交申请**,管理员审核通过后提升等级与对应权限,记录留档作为证据链。
- 首批判定与单人临时权限:冷启动时没有达标用户,首批名单的判定以及是否启用"单人临时权限"(让个别用户先行获得较高境界)**由 admin 决定**;后续用户量起来后,再演进为"构境及以上三人审核"的众审模式,由管理员兜底。
- 术语对照:「我的」页展示的**学分**即服务端现有积分(credits,`knowledge_point_credits`);**勋章**对应客户端现有 achievements(`app/lib/learning/achievements.dart`)的落地展示;**证书**为新增概念(达到某境界或完成某分类时颁发,需新表)。

## 三、已知矛盾与缺口清单

### 1. 文档与实现漂移

- `README.md`:接口表只有 assets 7 端点,缺 /api/knowledge、categories、concepts、points、chapters、comments/corrections/review/credits、sage、devices data;README 写的 docker compose + MinIO 是目标形态,但实际启动脚本(`scripts/start-dev.ps1`、`server/package.json` 的 db:up/db:down/db:status)仍走 WSL + SeaweedFS,需要统一为 Docker(见 P0-3)。
- `server/.env.example`:注释仍写"WSL2 内由 systemd 管理",需随 Docker 化同步。
- `doc/数据库使用说明.md`:迁移清单停在 009,表结构仍是"九类→领域"两层,未含 parent_id、章节、评论/纠错/积分(010–016)。
- `doc/九类分类法.md`:第五节引用已删除的 `LearningDomain.categoryId` / `KnowledgeGraph.categoriesFor`,代码实际是 `ScholarCategory.parentId`。
- `doc/进展.md`:记录停在 010(智者),缺 011–016 相关的章节/评论/纠错/积分/分类树统一等步骤。
- `doc/design.md`、`doc/档案.md`、README 仍强调"档案只在本机、不上传",但 2026-11-12 第七步已把全部数据迁入服务端,本机只留设备 UUID 和缓存。**理念文档必须重新表述数据归属**。

### 2. 安全缺口

- 无认证/角色:全系统以 deviceId 为身份。
- `POST /api/knowledge/points/corrections/review`:任何人可审核,发积分数额(0–1000)由客户端自报。
- 智者贡献"提交即审批"(`010_sage_contributions.sql` 注释预留了 status 列,待人工复核启用)。

### 3. 闭环缺口

- 纠错审核通过后**只发积分,没有把 suggestedText 写回知识点内容**,纠错闭环未完成。
- 知识贡献没有审核队列(纠错有 pending 状态,贡献没有)。

### 4. 代码/体验缺口

- 消息已读状态只在内存(`home_page.dart` 注释自认"重启后再提示一次"),消息本身也是即时生成不落库。
- `KnowledgeCatalog.instance` 单例与 repository 拉取的 catalog 并存(`home_page.dart` `_addConceptPlan` 用单例而非 `_graph` 所属 catalog),有不同步风险。
- 档案只有导出,没有导入。
- 九类中六类为空(思辨/表达/对抗/制作/群治/自知之学),知识内容集中在教养/天地/生命三类。

### 5. 质量缺口

- server 无任何测试,不在 CI;验证手段只有 `npm run typecheck`。
- app 最新功能(评论/纠错/积分/章节/手风琴树)无单元测试。
- repository 里有两处防御性降级:`parent_id` 缺列→503,评论表缺表→静默空列表(`point_feedback.repository.ts`)。新库跑迁移前这些功能是"界面在、表不在"的空壳。
